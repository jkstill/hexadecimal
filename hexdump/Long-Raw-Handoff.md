# LONG RAW handoff

**Status on 22 November 2026, branch `long-raw`.** The experimental Java reader can read a complete `LONG RAW` beyond 32,767 bytes. On ATP, the dump formatter produced correct output through 2,097,153 bytes. The local databases lost Oracle server processes during client fetch. A later ATP run on the same day reproduced that disconnect, and a standalone test case with no hexdump code now reproduces it on all three databases. A ROWID variant of the iterator avoids the crash and passes the full test suite on local 26ai, local 19c and ATP. See "Standalone test case for the crash" and "ROWID variant of the iterator" below. The production package installer still supports BLOB and RAW only.

## Intended behavior

The proposed `hexdump_binary.hexdump_long_raw` takes a table, optional owner, column, filter, and optional NUMBER or VARCHAR2 bind. It should produce a separator for each source row, including NULL, then 16 bytes per data line with a zero-based hex address and printable ASCII. A final partial line matters even when it contains only one byte. The goal is a single query with bounded memory for large values. Copying a whole value into a staging table or temporary BLOB would defeat that goal.

## What DBMS_SQL could fetch

The first probes used a local 26ai database, release 23.26.1.0.0. It lacked the repository's `BINARY_TEST` fixture, so the read-only probes used `SYS.IDL_UB1$.PIECE` and its companion length column.

| Probe | Observation |
| --- | --- |
| Define and fetch as RAW | A 3-byte value returned 3 bytes with column error 0. A 57,339-byte value returned 32,767 bytes, reported actual length 32,767, and column error 1406 (truncation). Checking the returned length alone would miss the loss. The RAW fetch interface has no continuation offset. |
| `DEFINE_COLUMN_LONG` and `COLUMN_VALUE_LONG` | Oracle raised `ORA-00932` because the piecewise character interface expected character data. |
| SQL projection with `TO_BLOB(piece)` | Oracle raised `ORA-00932` on the actual LONG RAW column. |
| Nested cursor expression and top-level ref cursor | The nested cursor expression raised `ORA-00997`. A top-level PL/SQL `OPEN ... FOR` succeeded and described the column as type 24 (LONG RAW). This established cursor construction only. |

An older branch experiment used `INSERT ... SELECT TO_LOB(...)`. Staging was ruled out on size grounds. The older Java converter likewise copied the entire stream into a temporary BLOB. The session prototypes instead attempted to retain only the current stream and a small read buffer.

The alert logs identify server-process failures. They do not establish their root cause or identify a faulty Perl, OCI, JVM or database component.

Neither local run recorded which fixture was being fetched at the disconnect. The harness reads every size through one cursor, and the last verified size was 17 bytes on both databases.

## ATP results

The wallet alias was `/@jks26ai01`. The successful SQL*Plus connection used `ORACLE_HOME=/u01/app/oracle/product/21c`. ATP reported **23.26.4.1.0**. Initially `V$OPTION` reported Java available, but Java compilation failed with `ORA-29538` and `DBA_REGISTRY` had no JAVAVM entry. JAVAVM was enabled with the owner's approval, the instance restarted, and the component reached `VALID`. The isolated package compiled after omitting the repository's development session settings, which ATP rejected with `ORA-01031`.

The ATP fixtures contain a repeating 00 to FF byte pattern. Fixture ID 0 represents SQL NULL. ID -1 selects no row. Each larger value was selected individually on ATP. The local regression harness selected several source rows through the same iterator.

| Consumer | Coverage | Result |
| --- | --- | --- |
| Server-side PL/SQL cursor loop | NULL and 1, 16, 17, 1,999, 2,000, 2,001, 32,767, 32,768 and 2,097,153 bytes | Verified separator counts, offsets, hex, printable text, partial final lines and byte counts. All ten passed. Only the verification messages crossed back to the client. |
| 21c SQL*Plus, direct fetch | One 17-byte value | Returned the separator, 16 data bytes at address 00000000 and the final byte at 00000010. |

| Oracle 21c Perl, descending address sort on server | 1,999, 2,000, 2,001, 8,191, 8,192, 8,193, 32,767, 32,768 and 2,097,153 bytes | Perl checked each line and reassembled the bytes by address. Every SHA-256 matched. The largest case returned 131,073 data lines plus a separator. |

The local Perl harness used Perlbrew Perl 5.40.0 at `/opt/perlbrew/perl5/perlbrew/perls/perl-5.40.0/bin/perl` with DBD::Oracle 1.90. After the owner enabled access to the bundled interpreter, the ATP client check used `/u01/app/oracle/product/21c/perl/bin/perl` (5.38.2), DBI 1.644, DBD::Oracle 1.90 from the 21c Perl installation, and Digest::SHA 6.04. The ATP check requested a row cache of 100.

Sorting lets the database finish producing the dump before the client consumes the ordered rows, so the sorted results above say nothing about fetching across round trips. In those runs nothing larger than 17 bytes was fetched unsorted by a client. The change of interpreter was accompanied by a change in query shape, so no conclusion about Perl causing or fixing the disconnect follows from them.

**What this establishes.** The disconnect is not specific to the local databases, to Perlbrew Perl, or to `order by`. It does not depend on the size of the value being read. Reading one value across many client fetch calls works, as does closing the cursor early. Every failing case has a non-NULL source row that follows a row large enough to push it into a later client fetch call. Every passing multi-row case either ran inside one server call (the counts) or had all of its row advances inside the first fetch call (small leading rows), or advanced to a NULL.

ATP gives no access to the incident trace, and `V$DIAG_ALERT_EXT` returned no rows for the period, so the ATP failures are confirmed only as `ORA-03113` on the client.

## Standalone test case for the crash

The crash does not need the hexdump package, ODCI, pipelined functions or Perl. A Java stored procedure that keeps a server-side JDBC `ResultSet` over a LONG RAW column in a static field, driven from SQL*Plus one database call at a time, reproduces it. The step-driven test case uses two 20,000-byte rows. In the table below a vertical bar separates database calls, `o` is `executeQuery`, `n` is `ResultSet.next()` plus `getBinaryStream`, `r100` reads 100 bytes and `R` reads to the end of the value.

| Calls | Result on local 26ai, local 19c and ATP |
| --- | --- |
| `o n R n R n` | Passes. Everything is in one call. |
| `o` then `n R` | `ORA-03113` at `n` |
| `o n` then `R` | `ORA-03113` at `R` |
| `o n r100` then `R` | Passes |
| `o n r100` then `r100` then `r100` then `R` | Passes (26ai only) |
| `o n R` then `n R` | `ORA-03113` at the second `n` |
| `o n r100` then `R` then `n R` | `ORA-03113` at the second `n` |

The results were identical on 23.26.1.0.0, 19.12.0.0.0 and ATP 23.26.4.1.0. The same sequence against a `RAW(2000)` column passes on all three. On local 26ai each failure wrote `ORA-07445: exception encountered: core dump [__intel_avx_rep_memcpy()+160] [SIGSEGV] [ADDR:0x0]`, for example incidents 47170 and 46706.

Stated as rules: for a LONG RAW column on the server-side internal JDBC connection, `executeQuery`, `next` and the first read of the value must all happen in the same database call. After the first read, the rest of that value can be read across any number of calls. Advancing the cursor to another row in a later call always kills the server process. Whether Oracle regards this as a defect or as an undocumented restriction of LONG streaming is for an SR to settle. The incident trace files on the local hosts are readable only by the oracle software owner, so the call stacks were not collected.

## ROWID variant of the iterator

The ROWID variant follows those rules. The filter clause now selects ROWIDs, which are not LONG data and can be fetched across calls. For each ROWID the Java reader prepares a single-row statement, executes it, positions on the row and reads the first chunk of up to 2,000 bytes, all inside one call. Later chunks of the same value are read as the client fetches.

With this variant installed under the `HXATP_*` names, the following all passed on local 26ai, local 19c and ATP:

- The server-side check and the mixed direct/sorted Perl check, 13 fixtures.
- Unsorted single-row client fetches of all 13 fixtures.
- Every multi-row case that failed above, plus all rows through one cursor with requested row caches of 1, 2, 3, 7 and 100.
- The original regression harness, unmodified apart from the package name, including its early-termination and reuse checks.
- The early termination check. Session PGA maximum after a full 2,097,153-byte dump was about 16 MB on the local databases and about 30 MB on ATP.

A first version of the variant, which left the first read to a later call, passed on ATP but failed on both local databases with a requested row cache of 1. That is how the second rule was found.

**Consequences of the variant.** The ROWID query and the per-row statements are separate statements, so they are not read consistent with each other. A row deleted after the ROWID query ran is dumped as an empty value. The filter must be valid against a `select rowid from <table>` statement, so the source must be a table that has ROWIDs.

**Still open.** Server memory growth was measured at one size only, and nothing larger than 2,097,153 bytes has been tested. The variant has not been merged into the package installer. Both integration patches, including the new one, still carry the `safe_to_print` change described below.

## Test scripts and prototype sources

The links below are relative to this handoff. The ATP test scripts are archived copies of the temporary files used during the session, and the first four hard-code the `jks26ai01` alias. Fixture loaders create their own test table and the consumers expect the isolated ATP package. They are historical test artifacts, separate from the package installer.

All three PL/SQL integration patches also change the shared `safe_to_print` function, which the existing BLOB and RAW dumps use. It now derives the byte value with `to_number(rawtohex(...))` and `chr` in place of `utl_raw.cast_to_varchar2` and `ascii`. The reason was not recorded.
